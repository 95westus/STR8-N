# Beta28 on board 2512

Hardware qualification passed after physical RESET: beta28 A booted, all
131,072 flash bytes matched the installation plan, and all four native
utilities passed launch/query/exit checks. The complete 131,072-byte SRAM
image is unchanged, as are RTC history, identity, EEPROM and calibrated
trim (-12). EDU remains ON. The qualification receipt is
`BUILD/v2-beta28-b23/hardware-qualification-2512.json`.

The installation uses `BUILD/v2-beta28-b23`, a beta28 variant for 2512's
registered beta25 recovery ABI. It retains fixed B3:F, the active beta25
monitor in slot B, B0, CLOCK in B1:B000-DFFF, and the resident RTC/SPI code
and identity/configuration records. Beta28 is installed in slot A.

All proposed writes are bound to two matching complete flash reads. The
installer is rehearsed against those exact images, rejects stale preimages
and corrupt transfers, executes flash workers in RAM, and commits the new
monitor last. There are 14 sector erases, recorded in the wear journal.
Physical RESET and final complete flash/SRAM/device readbacks are required
before a hardware qualification receipt is issued.

The variant changes the boot compatibility token and slot-validator calls
without changing utility offsets or RAM reservations. A directory fix also
excludes reserved B2 from the legacy S/R/T record scan. Otherwise `T` could
mistake native utility bytes for an SR header and print a phantom program.
The replacement is the same size and preserves shared extension entry
addresses. The original generic offline candidate does not include this
directory fix and remains reference-only, not an installation package.

Utility flash occupies 20,450 of 22,528 reserved bytes, leaving 2,078 bytes.
Normal active utility RAM reservations, excluding monitor/service RAM,
zero page and stack, remain:

| Utility | RAM bytes |
| --- | ---: |
| MAINT | 5,232, plus 4,096 during sector writes |
| SRAM | 736 |
| WORK | 847 |
| EDU | 124 |

The original CLOCK 1.6 saved program is retained unchanged. Its command set
does not include the newer BATTERY controls. The beta28 startup reminder
mentions CLOCK BATTERY; configuring that reminder requires CLOCK 1.8 to be
loaded separately or a later saved-CLOCK update. The four native utilities
and the monitor have been upgraded; CLOCK has not.

2512's repeated
SRAM readbacks contain no valid saved-program layout header. The installation
does not format SRAM or create a CLK record. `R CLOCK` remains available;
`R SRAM` followed by `G CLK` requires a valid directory and a saved CLK first.

## Possible use of the spare utility space

No command chaining is implemented by this release. Of the proposed forms,
`R SRAM;G CLK` communicates two sequential commands most clearly. Supporting
it requires an explicit handoff to the SRAM interpreter and stopping the
second command if launch fails. It must not rely on UART typeahead, which
programs can flush or consume at different prompts. The SRAM manager must
copy any pending command before loading a program over application RAM.

`|` conventionally denotes a data pipe; quoted commands require additional
parsing/escaping rules; trailing words alone are ambiguous. Another compact
design is an explicit one-shot SRAM launch command rather than a general
queue. Future payload sizes need assembly measurements: 2,078 bytes are
inside B2, not spare space in the nearly full monitor command dispatcher.

Other useful candidates are a compact utility/version/RAM-ownership display,
read-only saved-program integrity checks, and a combined battery-age and
flash-wear status view. These are proposals, not installed features.
