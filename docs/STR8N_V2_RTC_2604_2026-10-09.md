## Automatic and manual analysis

The existing **Calibrated board drift every 3 hours** automation now uses the
new three-RTC baseline index. Its schedule, chat destination and reporting
preferences remain unchanged. Future runs are read-only; they do not apply
trim proposals or SET UTC. Board 2512 remains explicitly RTC unavailable.

Manual analysis uses the same acquisition/reporting workflow:

```text
python tools/analyze_rtc_drift.py
```

The tool resolves current ports by USB serial, verifies baseline report hashes,
checks trim/control/EUI, takes fresh NIST measurements and retains successful,
unique historical checks using each board's unchanged baseline. Older two-board
calibrated histories remain usable for their donor boards; 2604 begins its own
history at enrollment. A failed port or acquisition stops the complete run and
retains the failed evidence. No failed/stale acquisition replaces a new sample.

Each completed run writes `summary.json`, `clock-drift.png`,
`calibration-fit.png`, their SVG versions, measurements/statistics/uncertainty,
residual and trim-prediction CSVs. Bounds, historical standard deviation and
fitted residual uncertainty remain distinct. A short first 2604 interval cannot
establish a reliable residual rate; retain -16 until its own data supports a
change. UTC/trim changes require a new baseline.

The initial three-board capture/report was verified under
`output/qualification/rtc-residual-drift-2026-10-09-212333Z`. All three status
and fresh-NIST measurements passed; charts and CSVs were generated and visually
checked. 2604's first comparison spanned only 0.0387 hours, so its broad ppm
bounds support no trim change. Reports explicitly retain -18/-14/-16.
An initial plotting dependency mismatch was retained in the run logs and fixed
by selecting matching interpreter wheels; chart generation then passed with
both the installed Python 3.13 and bundled Python 3.12 runtime. The final
`onboarding-summary.json` pins the baseline, successful report and persisted
automation prompt hashes.
