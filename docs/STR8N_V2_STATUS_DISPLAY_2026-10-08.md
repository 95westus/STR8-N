# Boot and EDU status display: unflashed beta16 candidate

The owner-selected layout keeps CPU RAM independent of EDU and uses the same
formatter for monitor entry and EDU 1.1. The candidate is built/model-tested
locally under `BUILD/v2-status`; the boards still run installed beta15/EDU 1.0.
No COM ports are opened and no boards are flashed by this work.

## Normal display

```text
STR8-N 2.0b16 B3 65C02
ABI 65C02 | 816E | 816N-VEC

RAM $0200-$64FF

EDU ON

RTCC: UTC 2026-10-08 19:53:15
RTCC: EUI 54:10:EC:B6:64:AF

SSRAM: PROGRAM payload 63488 bytes
SSRAM: WORKSPACE 65504 bytes

B3>
```

This example is generated by the model with a fixed calendar/EUI fixture,
not a new board capture or time synchronization. On the 816, the usual CPU/ABI
banner remains appropriate to that board. A latched outage retains its current
down/up and logging/acknowledgment messages in the RTCC block; automatic logging
is still confined to the original cold-boot path.

The RAM line uses the active kernel discovery limit. `EDU ON` identifies the
enabled service mode and does not certify connected or working hardware. An
absent/rejected service component can still publish the earlier fail-safe
RAM limit independently of that setting. With explicit OFF:

```text
RAM $0200-$66FF

EDU OFF
```

OFF omits both device blocks, performs no I2C/SPI transactions and leaves all
512 reclaimed bytes untouched. Flash program storage remains available.

## SPI SRAM allocation

`SSRAM` means the EDU's 23LCV1024 SPI SRAM. These are configured capacities,
not remaining free bytes. The 2-KiB management region is excluded from program
payload; the last 32 bytes remain reserved for the existing explicit probe.

| Program allocation | PROGRAM payload | WORKSPACE |
| ---: | ---: | ---: |
| 16 KiB | 14,336 bytes | 114,656 bytes |
| 32 KiB | 30,720 bytes | 98,272 bytes |
| 48 KiB | 47,104 bytes | 81,888 bytes |
| 64 KiB | 63,488 bytes | 65,504 bytes |

The query reads/validates the committed layout, its CRC, fixed/reserved fields,
revision and boundary. It accepts the legacy fixed 64-KiB program layout for
reporting only. If the primary is uncommitted, a verified modern secondary
reports `SSRAM: Layout needs repair` without repairing it. Other states are:

```text
SSRAM: Allocation uninitialized
SSRAM: Layout invalid
SSRAM: Unavailable
```

No default 64/64 split is assumed when there is no valid layout. No formatting,
upgrade, repair, resize, reclaim, claim/release, epoch initialization, or explicit
SRAM PROBE occurs. SRAM array/metadata bytes stay unchanged. The driver may
temporarily select sequential transfer mode for the READ, then restores the
original byte/page/sequential mode. The 64-byte CPU transfer window at
`$6400-$643F` is backed up and restored on success, invalid metadata, short read,
and service failure. `$66AE` write denial and `$66AF` live-handle/reset latch
are not changed. Public foreground/discovery calling rules remain unchanged.

## EDU 1.1 operation

The status block appears automatically before the first prompt. `?` repeats
the block; the short command list appears once. RAM and device figures always
describe the active state. A different saved mode adds a separate pending line:

```text
EDU 1.1

RAM $0200-$64FF

EDU ON
EDU after RESET: OFF

RTCC: UTC 2026-10-08 19:53:15
RTCC: EUI 54:10:EC:B6:64:AF

SSRAM: PROGRAM payload 63488 bytes
SSRAM: WORKSPACE 65504 bytes
ON OFF ? Q
EDU>
```

ON/OFF still require a single `Y` at `Apply after RESET? [y/N]:`; Enter or
other answers cancel. An unchanged saved mode reports `No change.`. Saved
changes take effect only at RESET. Status inspection inside EDU suppresses
boot power-fail save/ACK behavior, leaving live evidence and EEPROM untouched.
The original boot power-fail diagnostic is retained around EUI printing.

## Size, placement and pairing

The **1,024-byte sealed asset at B2:C900-CCFF** contains 1,021 linked code/table/
state bytes and padding/seal. It occupies spare space in already-used sector C;
no new flash sector is allocated. The bank-safe RAM worker copies it into
**temporary monitor staging `$7000-$73FF`**, then checks the complete CRC and
`BS`,1,1 header before execution. Missing/corrupt assets report
`Status unavailable` and retain the normal monitor and service reservation.

The existing E gaps hold a 110-byte mode/print helper at EE92-EEFF and a
251-byte checked loader at EF00-EFFA. The shortened APPS extension-help string
uses E7F4-E7FD; all eight application descriptor slots remain intact. First-
half and complete E seals are recomputed. The main E launcher remains 1,754
bytes and both monitor slots remain within 3,968 bytes. RTCC/banner/SPI helper
code uses 1,255 bytes within its existing allocation. Fixed recovery F stays
byte-identical. No additional permanent user-RAM reservation is introduced.

EDU 1.1 is **611 bytes at `$2000-$2262`**, with a 635-byte ordinary saved record
that still fits B2:C600-C87A. WORK 1.1 and SRAM 1.1 are unchanged. The formatter
avoids RTC binding scratch at `$6D00-$6D3C` and outage/SPI scratch at `$6B00`.
As with other staging users, reload SRAM after normal monitor return or other
staging use; application programs cannot retain their own data in monitor
staging RAM.

The candidate E helpers have signature `ED`,1,2 at EE92. EDU 1.1 is built for
that signature and its checked entry addresses. A future installer must pair
the candidate firmware, sealed status asset and EDU utility, preserve existing
records/EUI tail and account for erases. No such installer is executed here;
the installed beta15 receipts and hardware readbacks remain historical evidence.

## Local reproduction

```text
python tools/build_v2_status.py
python tools/build_v2_edu_utility.py --build BUILD/v2-status
python tools/test_v2_status.py
```

Focused linked-code models verify exact ON/OFF layout, all four allocations,
legacy/recovery/corrupt/uninitialized layouts, missing SRAM, all three chip
transfer modes, automatic EDU status, pending-mode confirmation/reset,
caller-buffer and live-epoch preservation, latched-outage read-only inspection
and missing/corrupt asset refusal. Generated model transcripts are in
`BUILD/v2-status/boot-status`; they are model output, not board captures.
Existing kernel/SPI/RTCC/TIME/EUI/CLOCK regression models are run against the
candidate in isolation. Raw evidence and generated artifacts remain ignored.
The final `tools/audit_v2_status.py` check passes, binding the sealed asset,
EDU 1.1, source hashes, exact-output/preservation tests and all service/workspace
reports. The workspace suite includes all 651 interrupted-write checkpoints.
The Git/history/release-ZIP no-board-backups audit also passes. No physical
board test, flash update, commit or push is performed for this candidate.
