# 2604 crypto detection/status RAM qualification

Recorded 2026-10-14. The owner released board 2604 for this work. Only 2604
(USB identity A10MQGVHA, COM5) was opened by the crypto qualification tool.
The overnight soak's existing exclusion of 2604 was retained. The shared
serial coordinator provided exclusive access between other-board batches.

## Observed device and candidate

The device at seven-bit address $60 returns revision `00 00 60 03`, identifying
an ATECC608B rather than the ATECC608A named in the EDU documentation. The
engine now accepts exactly `00 00 60 02` (A) and `00 00 60 03` (B). Other
revisions remain unrecognized; the code does not infer a factory provisioning
variant from revision alone.
[Microchip revision differences](https://onlinedocs.microchip.com/oxy/GUID-91D4A0CB-3AFD-443D-B23E-4D22AD0B49DB-en-US-1/GUID-46FD2FED-DEA0-4C69-B301-DDD5359198AD.html).

The A/B engine is 778 bytes. The complete RAM adapter candidate is 1,811 bytes
at $2000-$2712, SHA-256
`0a8bf1b90249e624d39e831bee05e76d63bd34c4cfecd6348b70ee8ee9e66198`.
It remains disabled by default; this test explicitly selected $60 and the
project's nominal 8 MHz profile. No resident command or firmware installation
has been added. ADC is excluded.

Three repeated physical calls returned:

| Field | Observation |
| --- | --- |
| Result / validity | Present / all three public-field validity bits set |
| Silicon revision | 00 00 60 03, ATECC608B |
| Public serial | 0123DE7CADBDB846EE, identical on all calls |
| LockValue / LockConfig | 55 / 55: data/OTP zone and configuration zone unlocked |
| Field errors | All zero |
| Sleep cleanup / STOP error | Both zero |
| RTC status before / after | Both zero on every call |
| RTC control / trim | 00 / 0C, unchanged across every call |

No key-slot contents were read. Unlocked zones do not establish whether useful
keys are provisioned. Only Info revision and the four planned public
configuration-word reads were sent by the crypto engine. No provisioning,
Lock, Write, key-generation, OTP or data-zone command was part of this probe.

## Hardware harness and preservation checks

[qualify_v2_crypto_board.py](../tools/qualify_v2_crypto_board.py) stages the
candidate and a monitor-return wrapper in ordinary RAM. The monitor correctly
refuses direct I/O dumps, so a separately saved/restored RAM helper reads only
VIA DDRA, non-handshake Port A and PCR during preflight.

HOLD clears the shared provider's code-verified ready bit. Immediately before
crypto, the wrapper calls the existing read-only RTC STATUS gateway to perform
normal provider revalidation. It checks RTC status again after crypto and
captures raw RTC registers. This initializes no crypto settings and does not
set the clock or acknowledge power failure. A model test executes this wrapper
with the actual linked shared gateway/provider starting from ready=2.

The wrapper compares DDRA, driven VIA outputs, PCR, stack pointer and I/D flags
across each crypto operation. All comparisons passed. It checks the released
shared lock, public-field errors and cleanup/STOP results. RTC ST, running,
backup and power-fail bits, control and trim remained unchanged; ordinary time
progression is allowed. The status consumer must still show field and cleanup
errors separately from Present.

Before staging, the harness reads the overwritten $2000-$2AFF RAM range twice
and saves it. It reads all four flash banks before and after the probe, with
no flash programming path. Restoration uses a load-only uploader that ignores
the S9 entry address and never issues G. Final preservation results and hashes
are recorded in the owner-local run receipt.

Evidence: `output/qualification/crypto-status-2604-2026-10-14-r6/probe/`, including
the serial transcript, original/restored RAM package, each call's RAM snapshot,
and prior/final bank images. The final report records `passed`, `ram_restored`
and `flash_unchanged` as true. All four final bank images match their
pre-probe images byte-for-byte, and the complete overwritten RAM range matches
its repeated pre-probe backup. The board was left at the B3 monitor with its
existing firmware and service reservation intact.

## Initial-run loader incident and recovery

The first A-only run safely returned Unrecognized device for the B revision,
without public configuration reads, and completed Sleep cleanup. During RAM
restoration, the host harness mistakenly used Link.monitor_load, a helper that
also issues G to start its loaded image. It started the saved RAM contents and
the board stopped responding. The owner pressed physical RESET when requested.

Recovery independently verified the complete saved RAM range was already
restored, compared all four flash banks byte-for-byte with the pre-probe images,
and confirmed an idle bus and released service lock. All passed. Evidence is
under `output/qualification/crypto-status-2604-2026-10-14-r5/recover/`.
The initial run's receipt retains the incident and recovery; it is not relabeled
as a successful A-only qualification.

The harness now uses an explicit load-only path for both staging and restoration.
A regression test loads a saved image starting with STP and verifies that no
G command is sent, including when readback fails. The corrected physical run
uses the revised harness. No host-issued reset, erase or installation command
was added to recover from the incident.

or electrical wake/rise-time measurements. Model timings remain cycle-based;
host command elapsed times include gateway, console and serial overhead.

installation remain pending. The offline build manifests retain their offline
provenance; physical evidence is bound separately to the candidate hash.
